# IP 封禁（418 / -1003）作为保护模式的一等触发源

**Status**: accepted（2026-10-22 · 本轮需求讨论 · Round 1 Q5 + 调研回填）

首版只调用币安**公开**行情（现货 + USDⓈ-M 永续），而「保护模式」（GLOSSARY 定义）此前只有「连接中断」这类**理论**触发源。实测证明存在一个**已经发生过**的触发源：本机出口 IP `66.90.98.34`（经本机代理 `127.0.0.1:7890`）被 USDⓈ-M REST **直接 418 封禁**，而同刻现货主机正常 200。官方对 418 的定义是：**「收到 429 后继续发送请求」导致的自动 IP 封禁**——它不是限流，是行为惩罚。

**决定：把 418 / `-1003` 定为保护模式的一等触发源**，并对其施加以下硬规则：

1. **收到 418 立即停止该类请求，不重试**；把响应里的 **`Retry-After`（秒）当硬截止**读，而不是建议值。
2. **按 IP 做全局出站预算**：限额按 **IP** 而非 API key 计算，因此本机所有出站脚本（既有计划任务 + 新工作台）**共享一份配额**，必须有**一处统一的出站闸门**，而不是各脚本各自限速。
3. **稳态占用压低**（目标 ~20% 以下）、单线程、读 `X-MBX-USED-WEIGHT-*` 作为实际占用的事实依据。
4. 触发后进入保护模式：暂停新增模拟风险、保留虚拟持仓与事件记录；退出必须走**恢复前检查 + 人工明确确认**（沿用既有定义，不新造流程）。
5. 实时行情**优先推送式 WebSocket**（`-1003` 的官方文案本身就建议改走 websocket）。

## Considered Options

- **重试到成功**：否，而且是被**实测**否掉的。「收到 429 后继续发请求」**正是** 418 的触发条件；本会话 2026-10-22 20:53 那批探测（为**发现**封禁而做）已直接观测到 `banned until` 被**推后**（`…835787` → `…753316` → `…319872`）。重试不是恢复手段，是加重手段。
- **只降速、不设保护模式**：否。降速是**预防**，解决不了「已经封了」的既成事实；已经封禁时系统仍会试图下单/记录，必须有一个显式的停摆态。
- **把封禁当普通网络故障、静默重连**：否。静默重连会把「正在被惩罚」伪装成「正在恢复」，与「不能静默」的既有纪律冲突。

## Consequences

- **「永续实时行情」在规格里必须标为条件性交付**：官方文档**未陈述**「REST 已被封的 IP 能否建立推送式 WS 连接并收到公开行情」——本仓调研检索了现货四份文档、期货 general-info 与官方 `llms-full.txt`（8.28 MB）全文，**均无此陈述**，唯一一手间接证据是 `-1003` 文案主动建议改走 WS。另注：WS（推送流）与 REST 是**两套独立计数体系**（WS：5 条入站消息/秒、1024 订阅/连接、300 连接尝试/5 分钟/IP），但这**不构成**「被封 IP 的 WS 可用」的证明。因此首版不得承诺永续实时行情可达。
- **本决策不改变任何权限边界**：仍然不接私有 API 密钥、不查真实账户、不提交真实订单；封禁处理只影响**出站请求预算与停摆语义**。
- 区分 418 与地域限制的最简判据：**看有没有「到期时刻」**——418 一定带 `Retry-After` 或 `IP banned until` 文案；地域限制不会承诺「等到某时刻就恢复」。
- 重复者的封禁时长按 **2 分钟 → 3 天**递增；这意味着一次夜间无人值守的失控重试，代价可能是一整个交易日不可用。
